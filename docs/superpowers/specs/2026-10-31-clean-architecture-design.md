# Реорганізація eBay Copy Assistant

Дата: 2026-10-31. Напрям погоджений користувачем: поступова реорганізація зі збереженням поведінки та звичайного JavaScript. Цей документ описує межі реалізації для фінального перегляду.

## Мета

Зробити залежності явними, відокремити правила роботи від Chrome API та DOM і надати кожному модулю одну зрозумілу відповідальність. Зберегти роботу розпакованого Manifest V3 розширення без обов'язкового збирання. Не додавати фреймворк, TypeScript, контейнер залежностей або бібліотеки виконання.

## Поточний стан

- `background.js` містить маршрутизацію, валідацію, сценарії запитів, завантаження опису та кеш фотографій.
- `ui.js` містить представлення eBay, читання налаштувань, формування промпту та запуск Gemini.
- `extractors.js` читає DOM, отримує зовнішній опис і формує промпт. Навіть форматування залежить від `window.location`.
- `gemini-content.js` керує сценарієм, відображає статус, реконструює файли та організує відновлення після помилок.
- `request-store.js` поєднує сховище, строки придатності, сигнали очищення та переходи станів.
- `config.js` об'єднує політики URL, повідомлення, обмеження, налаштування та селектори eBay.
- Порядок завантаження задається маніфестом, `importScripts` та HTML. Тести повторюють списки файлів і виконують скрипти через `new Function`.
- Пакування містить окремий перелік файлів; поточне копіювання розраховане на плоску структуру.

Вихідна перевірка перед проєктуванням: 14 тестових файлів, 153 успішні тести; Biome успішний. У робочій копії є попередні незакомічені зміни інтеграції Gemini, UI, тестів і скілів. Реалізація має зберегти їх, а не відновлювати стан останнього коміту.

## Варіанти

1. Перенести файли по папках: мінімальна зміна, але змішані відповідальності залишаються.
2. Поступово виділити правила, сценарії та адаптери: обраний варіант. Проміжні кроки перевіряються на робочому розширенні.
3. Повне переписування з новим інструментарієм: більший обсяг і ризик без необхідної для цього проєкту користі.

## Структура й напрям залежностей

```text
src/
  domain/           правила URL, протокол і ліміти, промпт, переходи запиту
  application/      сценарії eBay, фонових запитів і підготовки Gemini
  infrastructure/   Chrome storage/tabs/runtime/alarms, fetch, кеш вкладень
  ebay/             селектори, DOM-читачі, вибір фото, представлення
  gemini/           редактор, DOM-вкладення, статус, спостереження URL
  options/          HTML/CSS і контролер налаштувань
  entrypoints/      підключення конкретних залежностей і реєстрація подій
```

`domain` не читає `chrome`, `window`, `document`, `navigator` або мережу. Час, URL сторінки та налаштування передаються аргументами. `application` отримує потрібні операції через звичайні об'єкти залежностей. Адаптери реалізують ці операції; точки входу створюють і з'єднують їх. Представлення показують стан і викликають передані обробники, не керують збереженням або бізнес-правилами.

Модулі залишаються класичними скриптами, сумісними з поточним способом запуску. Кожен модуль публікує один іменований API або фабрику в просторі імен розширення; внутрішні функції закриті. Глобальний простір використовується для завантаження й композиції, а не як приховане джерело залежностей сценаріїв. Перехід на ES modules та додавання збирача не входять у цю зміну.

Селектори й DOM-таймінги належать адаптерам відповідного сайту. Ліміти промпту, фото та строки придатності належать політикам. Назви повідомлень зберігаються як спільний контракт.

## Межі основних компонентів

### Правила

- Формування промпту: вхід — преамбула, дані товару, URL і ліміти; вихід — поточний текст без зміни форматування, маркерів та обрізання.
- Правила URL: чисті перевірки чинних дозволених адрес. Перенесення не розширює прийняті адреси або дозволи.
- Модель запиту: чисті операції для `pending`, `attaching`, `failed_partial`, `waiting_for_chat`, обчислення строку придатності та списків завершених/невдалих фото. Збереження чинних відмінностей записів із фото й без фото; зміна формату сховища не потрібна.

### Сценарії

- eBay: отримати підтверджений вибір фото, прочитати дані й налаштування, сформувати промпт, спробувати копіювання, надіслати START. Скасування вибору не створює запиту.
- Фонові запити: окремі іменовані обробники старту, отримання, підтвердження тексту, підготовки/повтору фото, отримання частин, підтвердження фото, продовження та збереження звіту. Маршрутизатор перевіряє повідомлення й відправника перед викликом сценарію.
- Gemini: отримати запит, підтвердити вставлення тексту, підготувати файли, додати їх через DOM-адаптер, підтвердити фото, відправити за чинними правилами, дочекатися URL звіту та зберегти його. DOM-редактор зберігається окремо від даних запиту.

Не створювати універсальну шину подій або окремий клас для кожного повідомлення. Достатньо невеликих фабрик та іменованих функцій, згрупованих за відповідальністю.

### Адаптери

- Сховище запитів забезпечує читання, запис і видалення. Сценарії застосовують правила та планують очищення через адаптер alarms.
- Сховище звітів зберігає поточні ключі `chat_*`, порядок, квоти й повторну спробу після очищення. Читання звітів та налаштувань в UI проходить через адаптери.
- Мережа відповідає за таймаути, завантаження й чинні обмеження фото. Кодування частин не потребує завантажувального коду в контексті Gemini.
- Кеш байтів залишається тимчасовою оптимізацією service worker. Стан запиту живе в session storage; наявність кешу не є підтвердженням завершення. Поточний сценарій помилки при втраті кешу зберігається; новий механізм відновлення не додається приховано.
- DOM-адаптери відповідають за читання eBay, парсинг HTML опису, вставлення в Gemini, підтвердження вкладень та відображення статусу.

## Незмінна поведінка й обробка помилок

- Зберегти дозволи, домени, порядок перевірок відправника та формат повідомлень/відповідей.
- Зберегти вибір фото, обмеження розміру, перевірку MIME та кількості байтів, порядок підтверджень і очищення.
- Зберегти захист чужої чернетки та явну дію її заміни.
- Зберегти автоматичне відправлення нового запиту лише після підтвердження тексту та вкладень; повторний запуск не відправляє його знову.
- Зберегти відновлення частково невдалих фото, ручне продовження та припинення автоматичних дій за непевного результату вкладення.
- Зберегти відстеження URL після невдалого автоматичного відправлення і заборону збереження початкової адреси як нового звіту.
- Зберегти повідомлення про оновлений контекст розширення та доступність кнопок.
- Помилки побічних операцій перехоплюються на межах сценарію/події. Не приховувати невдачу критичного ACK як успішне завершення. Невдале копіювання лишається некритичним.

Потенційні зміни поведінки, знайдені під час перенесення, документуються окремо. Не виправляти їх непомітно в межах структурної зміни.

## Порядок перенесення

1. Зафіксувати поведінку наявними тестами; створити спільні допоміжні засоби завантаження скриптів для тестів.
2. Виділити чисті правила промпту, URL і запитів; перевести поточні виклики на нові API.
3. Відокремити Chrome/мережеві адаптери й фонові сценарії; залишити точку входу тонкою.
4. Розділити eBay: DOM-читання, отримання опису, представлення та сценарій запуску.
5. Розділити Gemini: статус, складання файлів, спостереження URL і сценарій. Зберегти вже змінені редактор та вкладення.
6. Перенести налаштування й решту файлів у цільову структуру; узгодити маніфест, `importScripts`, HTML, шляхи тестів, README та пакування. Видалити тимчасові сумісні обгортки після оновлення всіх викликів.

Кроки можуть об'єднуватися для атомарного оновлення шляхів, але перевірка має відбуватися після кожного завершеного логічного перенесення. Лендінг, документи, іконки, CI та інструменти релізу залишаються поза `src`, крім потрібного оновлення посилань.

## Перевірка

- Чисті правила перевіряються без jsdom і моків Chrome: формат промпту, обмеження та переходи/строки придатності.
- Тести сценаріїв перевіряють порядок дій і припинення після відмов через передані залежності.
- Зберегти існуючі регресійні DOM-тести редактора, вкладень, вибору фото та UI. Оновлювати шляхи, а не прибирати перевірки поведінки.
- Додати перевірку меж залежностей для заборони браузерних глобалів у domain і прямих Chrome-викликів у application.
- Перевірити фактичні списки скриптів маніфесту та імпортів worker, а не дублювати застарілі плоскі списки в тестах.
- Пакувальник створює потрібні підкаталоги й використовує явний перелік production-файлів. Перевірка ZIP контролює посилання worker, options, content scripts і значків, а також відсутність розробницьких файлів.
- Підсумкові перевірки: `npm test`, `npm run check`, `npm run verify:version`, пакування й перевірка ZIP у тимчасовій директорії. Не перезаписувати наявний `extension.zip` для перевірки.
- Якщо доступний браузер із розширенням, перевірити товар → вибір фото → Gemini → звіт, скасування вибору, повторний запит та чернетку. Без такого браузера явно вказати, що тести не підтверджують роботу на живій сторінці Gemini.

## Критерії завершення

Увесь runtime-код організований за зазначеними межами; точки входу лише з'єднують компоненти та події. Domain не залежить від браузера, application отримує побічні операції явно, представлення не керує сховищем. Немає подвійних реалізацій старих і нових модулів. Розпаковане розширення і ZIP використовують ті самі актуальні шляхи. Перевірки проходять, документація пояснює запуск і відповідальності, попередні зміни користувача збережені.
